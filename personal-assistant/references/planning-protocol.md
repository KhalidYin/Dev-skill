# Planning Protocol

三层计划体系 + 头脑风暴协议 + 子计划规范 + 执行中插入协议。

## 三层计划体系

```
PLAN.md             → 仪表盘层：只看"正在发生什么"，完成即移除指针
docs/dep/plans/<name>.md → 合同层：每个功能/模块的完整 Phase-Gate 实施方案
TASK_STATE.md       → 执行层：当前 Phase 内的单步进度
```

### 职责边界

| 信息 | PLAN.md | plans/<name>.md |
|------|:---:|:---:|
| 子计划名称和文件路径 | ✓ | - |
| 当前 Phase 和状态 | ✓ | - |
| 优先级排序 | ✓ | - |
| 子计划间依赖 | ✓ | ✓ (depends_on) |
| 预估总轮次 | ✓ | ✓ (estimated_rounds) |
| 最近完成记录 | ✓ | - |
| 延后清单 | ✓ | - |
| 目标和背景 | - | ✓ |
| 涉及范围（包含/不包含） | - | ✓ |
| 主文档影响（syncs_to） | - | ✓ |
| Phase 总览（目标/轮次/依赖/状态） | - | ✓ |
| 每个 Phase 的输入条件 | - | ✓ |
| 每个 Phase 的产出 | - | ✓ |
| 每个 Phase 的完成标准 | - | ✓ |
| 每个 Phase 的边界（排除项） | - | ✓ |
| 每个 Phase 的涉及文件 | - | ✓ |
| 关键决策记录 | - | ✓ |
| 执行中发现 | - | ✓ |

## 触发条件

以下任一情况进入规划流程：

- 用户明确说"帮我规划一下"、"先想清楚再做"、"plan this out"、"设计一下方案"
- 任务预估超过 3 个 DEVLOG 轮次
- 涉及多个模块或功能，需要排序
- 新技术栈引入或跨模块大重构

### 决策矩阵：是否需要新建子计划 + 头脑风暴

| 场景 | 子计划 | 头脑风暴 | 理由 |
|------|:---:|:---:|------|
| 全新功能模块（如：添加支付系统） | 必须 | **必须** | 技术选型、架构影响需要用户拍板 |
| 引入新技术栈（如：Redux → Zustand） | 必须 | **必须** | 迁移成本、长期维护需要评估 |
| 跨模块大重构（如：前端整体改造） | 必须 | **必须** | 影响面大，方案需要用户确认 |
| 已有模块加小功能（如：用户列表加搜索） | 可选 | 轻量 | 2-3 个选项快速确认即可 |
| Bug 修复（原因已知） | 不建 | 不需要 | 直接写 TASK_STATE |
| Bug 修复（原因不明，需调查） | 可选 | 不需要 | 调查本身是第一 Phase |
| 配置调整、性能优化 | 不建 | 不需要 | 改动范围明确 |

### 轻量讨论 vs 正式头脑风暴

轻量讨论适用于已有模块加小功能：
```
1. AI 列出可行方案（推荐方案 + 1 个备选）
2. 用户确认或选择
3. 直接记录到子计划的"关键决策"中
4. 不需要单独的方案对比文档
```

正式头脑风暴适用于新功能/新技术/大重构，见下文。

## 模式一：正式头脑风暴（新功能 / 新技术 / 大重构）

### 触发

- 全新功能模块（项目之前没有的）
- 引入新技术栈或框架
- 跨模块大重构（影响 ≥ 3 个模块）
- 用户明确说"头脑风暴一下"、"先讨论方案"

### 流程

头脑风暴是多轮交互的独立过程，不直接改动代码。输出最终成为子计划的"背景"和"Phase 拆解"草稿。

#### Storm-R1：现状与目标确认

```
1. AI 阅读相关主文档和代码
2. 输出：
   - 当前状态：现在是怎么做的 / 没做的
   - 目标：要达成什么
   - 约束：技术债、时间、团队能力等限制
3. 用户确认或修正
```

#### Storm-R2：方案对比

```
AI 必须提出 ≥ 2 个可行方案，每个方案包含：

|  | 方案 A：[名称] | 方案 B：[名称] | ... |
|------|------|------|------|
| 概述 | [一句话] | [一句话] | |
| 优势 | [列举] | [列举] | |
| 劣势 | [列举] | [列举] | |
| 复杂度 | 低/中/高 | 低/中/高 | |
| 影响面 | [哪些模块受影响] | [哪些模块受影响] | |
| 与现有架构匹配度 | 高/中/低 | 高/中/低 | |
| 预估轮次 | N | N | |

推荐：[方案 X]，理由：[具体理由]
```

用户选择方案后进入下一轮。如果用户要求补充细节，AI 补充后再对比。

#### Storm-R3：范围边界确认

```
基于用户选择的方案，AI 输出：

## 范围
- **包含**：[明确要做的事]
- **不包含**：[明确不做的事，防止范围蔓延]
- **与已有子计划的边界**：[如果有的话]

## 主文档影响
完成后需要更新：
- PROJECT_SPEC.md：[新增/修改哪些章节]
- PROJECT_GUIDE.md：[新增/修改哪些架构描述]
- TEST_GUIDE.md：[新增/修改哪些测试说明]
- CODE_STYLE.md：[如果有新约定]

## 风险
- [风险]：[缓解措施]
```

#### Storm-R4：Phase 拆解初稿

```
AI 将范围拆解为 2-6 个 Phase 的初稿：

| Phase | 目标 | 预估轮次 | 依赖 |
|-------|------|---------|------|
| P1 | ... | ... | - |
| P2 | ... | ... | P1 |
...

用户调整后确认。
```

### 输出

头脑风暴完成后，AI 创建子计划文件 `docs/dep/plans/<name>.md`，将上述内容写入。同时在 PLAN.md 中注册。

---

## 模式二：轻量讨论（已有模块加功能）

### 触发

- 在已有模块上添加功能
- 改动范围明确（≤ 2 个文件）
- 不需要方案对比，只有一个明显的实现路径

### 流程

```
1. AI 简要说明实现思路（1-2 句）
2. 如果只有一种合理做法 → 直接确认；如果 2-3 种 → 列选项让用户选
3. 确认后直接进入 Phase 细化（跳过方案对比和范围确认）
```

### 输出

创建子计划文件（如需要）或直接进入 TASK_STATE.md。

---

## 模式三：Bug 修复（不建子计划）

### 流程

```
1. 原因已知 → 直接创建 TASK_STATE.md，进入 Development
2. 原因不明 → TASK_STATE.md Phase 1 = 调查诊断，完成后再决定是否需要子计划
3. 调查后发现需要大改 → 升级为轻量讨论或正式头脑风暴
```

## 子计划文件格式（plans/<name>.md）

### 文件命名

- kebab-case，与功能名对应：`user-auth.md`、`admin-panel.md`、`frontend-redesign.md`
- 不存在重名——一个功能一个文件

### 完整模板

```markdown
---
status: planning | in-progress | done
created: YYYY-MM-DD
updated: YYYY-MM-DD
priority: 1                    # 1=最高, 用于 PLAN.md 排序
estimated_rounds: 4-8          # 预估 DEVLOG 轮次

  - TEST_GUIDE.md
```

## UI 类 Phase 额外要求

UI 类 Phase 必须在细化时额外包含以下内容：

### 涉及页面/组件
```markdown
- 页面：`src/pages/Login.tsx` — 新建
- 组件：`src/components/LoginForm.tsx` — 新建
- 组件：`src/components/ErrorMessage.tsx` — 复用已有
```

### 组件树
```
App
└── LoginPage
    ├── LoginForm
    │   ├── EmailInput (受控)
    │   ├── PasswordInput (受控)
    │   ├── SubmitButton
    │   └── ErrorMessage (条件渲染)
    └── AuthRedirectLink
```

### 状态矩阵
| 状态 | 触发条件 | UI 表现 |
|------|---------|---------|
| 初始 | 页面加载，未输入 | 表单为空，按钮可点击 |
| 提交中 | 点击登录按钮 | 按钮显示"登录中..."，禁用 |
| 错误 | API 返回 401 | ErrorMessage 显示"邮箱或密码错误" |
| 成功 | API 返回 200 + token | 跳转到 /dashboard |
| 空数据 | 列表无数据 | 显示"暂无数据"占位图 |
| 网络错误 | API 无响应 | ErrorMessage 显示"网络错误，请重试" |

### 交互流
```
1. 用户输入邮箱和密码
2. 点击"登录"按钮（或按 Enter）
3. 前端校验：邮箱格式、密码非空
4. 调用 POST /api/auth/login
5. 成功 → 存储 token → 跳转 /dashboard
6. 失败 → 显示错误信息，保留表单内容
```

### 不做（UI 专属）
- 不做动画效果（后续迭代）
- 不做响应式移动端适配（另建子计划）
- 不做暗色模式（后续迭代）

## PLAN.md 格式（仪表盘）

PLAN.md 是仪表盘，不是实施文档。它只包含指针、状态、优先级，不包含 Phase 细节。

```markdown
---
updated: YYYY-MM-DD
---

# 项目计划

## 进行中
| 子计划 | 文件 | 当前 Phase | 已用轮次 | 开始日期 |
|--------|------|-----------|---------|---------|
| 用户认证 | [plans/user-auth.md](plans/user-auth.md) | P2: 注册/登录 API | R004-R006 | YYYY-MM-DD |
| 前端改造 | [plans/frontend-redesign.md](plans/frontend-redesign.md) | P1: 组件库选型 | R007-R008 | YYYY-MM-DD |

## 待开始
| 优先级 | 子计划 | 文件 | 预估总轮次 | 依赖 |
|--------|--------|------|----------|------|
| 1 | 管理后台 | [plans/admin-panel.md](plans/admin-panel.md) | 5-8 | 用户认证 P3 完成 |
| 2 | 数据导出 | [plans/data-export.md](plans/data-export.md) | 3-5 | - |

## 最近完成
> 仅保留最近 3 条。更早的直接移除（内容已在子计划文件 + 主文档 + DEVLOG 中）。

| 日期 | 子计划 | 已同步到 |
|------|--------|---------|
| YYYY-MM-DD | 数据库迁移框架 | PROJECT_GUIDE, PROJECT_SPEC |
| YYYY-MM-DD | 项目初始化 | PROJECT_GUIDE, CODE_STYLE |

## 延后
- OAuth 第三方登录 → 下个计划周期再评估
- 多语言支持 → 用户量上来后再考虑
```

### PLAN.md 维护规则

- **进行中**：每个活跃子计划一行。当前 Phase 和已用轮次每次 Gate 通过后更新
- **待开始**：按优先级降序排列。新子计划注册时插入到正确位置
- **最近完成**：保留最近 3 条。超过的直接删除——不移到别处
- **延后**：不需要立即处理的增强建议。下个计划周期时作为输入参考
- **状态一致性**：PLAN.md 中"进行中"的当前 Phase 必须与子计划文件的 Phase 总览一致

## 执行阶段的 Phase-Gate

### TASK_STATE.md 与子计划的关联

当存在子计划时，TASK_STATE.md 必须引用子计划文件和 Phase：

```markdown
## Goal
P2 — 实现注册/登录 API（子计划：plans/user-auth.md）

## Phase Context
- **输入条件**：[引用子计划中 P2 的输入条件]
- **完成标准**：[引用子计划中 P2 的完成标准]
- **边界**：[引用子计划中 P2 的边界]
- **上一 Phase 状态**：P1 done — 数据模型已就绪
```

### DEVLOG 中的子计划标注

每轮 DEVLOG 标题同时标注子计划和 Phase：

```markdown
### R007 [14:30] [user-auth] P2: 实现 POST /api/auth/register
```

无子计划时（单 Phase 的 bug 修复等）省略子计划标注：

```markdown
### R007 [14:30] 修复登录超时问题
```

### Gate 验证流程

当前 Phase 所有 TASK_STATE 项完成时：

```
1. 逐条检查子计划中该 Phase 的完成标准
2. 检查是否有越界改动（做了边界中排除的内容）
3. 检查"执行中发现"是否有新条目
4. 全部标准通过 且 无越界
   → 勾选完成标准，更新子计划 Phase 总览
   → 更新 PLAN.md（当前 Phase 推进到下一 Phase，或子计划完成）
5. 有未通过的标准
   → 补齐缺口，不进入下一 Phase
6. 有越界改动
   → 标记并询问用户："这个改动超出了 P2 的边界（[具体边界]），是否扩展到 P2 范围，还是拆分到后续 Phase？"
7. 有新的"执行中发现"
   → 分类处理，见下文
```

## 执行中发现 — 分类与处理

开发过程中暴露的问题，先记录到子计划的"执行中发现"区域，在每个 Phase Gate 时集中分类。

### 分类标准

| 类型 | 定义 | 处理 |
|------|------|------|
| **阻断** | 不处理会导致后续 Phase 无法进行或产生大量返工 | 在当前子计划中新增 Phase，调整依赖链 |
| **增强** | 显著改善质量，与已有未开始 Phase 自然关联 | 合并到相关未开始 Phase 的完成标准或产出中 |
| **延后** | 锦上添花，不影响当前子计划核心目标 | 移入 PLAN.md "延后"区域，进入下个计划周期 |

### 处理流程

```
Phase Gate 时发现新的 D 条目：

1. AI 逐条判断类型
2. 阻断型：
   - AI 提出新 Phase 的目标和预估轮次
   - 用户确认后插入子计划 Phase 总览
   - 更新依赖链
   - 更新 PLAN.md（如预估总轮次变化）

3. 增强型：
   - AI 说明建议合并到哪个未开始 Phase
   - 用户确认后更新该 Phase 的完成标准或产出

4. 延后型：
   - AI 将条目移入 PLAN.md "延后"区域
   - 在子计划的"执行中发现"中标注 → 延后

5. 全部处理完毕后，更新子计划文件
```

### 阻断型特殊规则

如果阻断条目很多（≥ 3 条且预估总轮次翻倍），考虑：
- 当前子计划是否范围过大？
- 是否应该将新增 Phase 拆为独立子计划？
- 向用户提出建议

## 执行中插入大模块

当已有子计划在执行中，用户提出一个新的大功能时：

### 插入协议

```
Step 1: 不打断当前 Phase
  - 当前正在执行的 Phase 继续跑完
  - 直到 Gate 窗口才处理新任务

Step 2: 快速评估
  - 新功能是否直接影响当前 Phase？（如果直接冲突，立即告知用户）
  - 新功能的优先级是否高于所有待开始的子计划？

Step 3: 头脑风暴
  - 新功能/新技术/大重构 → 正式头脑风暴（Storm-R1 到 R4）
  - 已有模块加功能 → 轻量讨论

Step 4: 创建子计划
  - 写入 docs/dep/plans/<name>.md
  - 在 PLAN.md 中注册到"待开始"区域
  - 如果优先级最高 → 放在待开始首位，当前子计划完成后优先执行
  - 不影响已在进行中的子计划（除非新功能直接冲突）

Step 5: 当前 Phase Gate 时告知用户
  - 当前 Phase 完成
  - 下一个是什么（可能被新插入的计划调整了顺序）
  - 新插入的排在哪里
```

### 原则

- **当前 Phase 不受干扰**：Phase 是原子执行单元，中断代价高
- **Gate 是唯一重排窗口**：所有排序调整在 Gate 时发生
- **用户决定优先级**：AI 建议但不代为决定

## 子计划完成与 PLAN.md 移除

### 完成验证

子计划所有 Phase 完成时：

```
1. 全部完成标准已勾选
2. 测试通过（如有）
3. 代码已 Review（如在 Review 模式）
4. DEVLOG 完整（每个 Phase 的轮次都已记录）

五项全部就绪 → 可进入同步阶段
```

### 同步到主文档

```
1. 按子计划 frontmatter 中 syncs_to 的清单，逐项更新：
   - PROJECT_SPEC.md：新增功能说明、技术决策、范围边界
   - PROJECT_GUIDE.md：新增架构描述、模块职责、数据流
   - TEST_GUIDE.md：新增测试说明、覆盖范围
   - CODE_STYLE.md：新增编码约定（如有）

2. 关键决策保存到 docs/main/memory/（写入或更新已有记忆文件）

3. 在子计划文件中标注"已同步"及日期
```

### 从 PLAN.md 移除

```
1. 将子计划行从"进行中"移到"最近完成"
2. 保留最近 3 条，超过的删除
3. 子计划文件（plans/<name>.md）不移除、不删除
   → 它是该功能的设计决策记录，持久保留
4. PLAN.md 只移除指向它的指针
```

## 快速规划（轻量模式）

适用于 1-2 个 Phase 的小任务，跳过头脑风暴和 4 轮交互。

### 触发

- 用户说"快速规划一下"、"简单列个计划"
- AI 判断任务只需要 1-2 个 DEVLOG 轮次
- 不涉及新技术或架构变更

### 流程

```
1. AI 直接提出目标 + Phase 拆解（含完成标准和边界）
2. 一轮确认
3. 写入子计划文件（plans/<name>.md）或直接写入 TASK_STATE.md
4. 在 PLAN.md 中注册（如建了子计划）
5. 即刻开始执行
```

### 快速规划不能跳过的内容

- 每个 Phase 的完成标准
- 每个 Phase 的边界（排除项）
- 这两项是防止漂移的最小必要信息
